# 跨平台注意力数据情况与 PCA 前预处理方案

本文说明 `20260619-20260627(1).csv` 的数据内容、可直接使用的字段、现有缺口，以及在进入 PCA 构造平台注意力变量之前需要完成的预处理。本文只覆盖 PCA 之前的步骤；PCA 载荷解释、主成分选择和后续 PEID 动力学建模不在本文范围内。

## 1. 数据概况

该 CSV 是一份内容级跨平台采集数据。每一行对应一次被采集到的平台内容或页面卡片，覆盖小红书、哔哩哔哩、抖音和快手四个平台。数据时间范围由采集时间 `created_at` 给出，从 2026-06-19 00:00:08 到 2026-06-27 23:58:51，共 50,446 条记录、45 个字段。

按平台划分：

| 平台 | 记录数 |
|---|---:|
| 小红书 | 17,010 |
| 哔哩哔哩 | 13,189 |
| 抖音 | 13,057 |
| 快手 | 7,190 |

按采集宏任务划分：

| 采集类型 | 记录数 |
|---|---:|
| 搜索浏览 | 23,772 |
| 推荐浏览 | 14,887 |
| 短视频推荐浏览 | 11,787 |

按页面类型划分：

| 页面类型 | 记录数 | 说明 |
|---|---:|---|
| `list` | 32,310 | 搜索或推荐列表中的卡片 |
| `reel` | 12,567 | 抖音、快手短视频流 |
| `note` | 3,279 | 小红书笔记详情 |
| `video` | 2,262 | B 站视频详情 |
| `content` | 28 | 少量快手内容页 |

## 2. 字段信息

### 2.1 内容字段

可用于识别内容主题、语义和视觉信息的字段包括：

| 字段 | 含义 | 当前情况 |
|---|---|---|
| `title` | 内容标题或卡片标题 | 约 96.7% 非空 |
| `content` | 正文、简介、卡片文字或自动抽取文本 | 约 96.5% 非空 |
| `media_summary` | 图片或视频画面的自动摘要 | 基本全量存在 |
| `author` | 作者或账号名 | 约 87.7% 非空 |
| `region` | 地区标签 | 大部分为 `无` |
| `publish_time` | 平台展示的发布时间 | 仅约 33.5% 非空，且存在异常日期 |

这些字段适合用于事件识别、关键词统计、主题过滤和内容去重。`publish_time` 暂不适合作为主时间轴，除非经过严格校验。

### 2.2 互动指标字段

可用于构造平台行为统计量 $y_{k,p,e,t}$ 的字段包括：

| 字段 | 含义 | 当前情况 |
|---|---|---|
| `likes` | 点赞数或获赞展示值 | 约 67.6% 非空 |
| `comments` | 评论数或评论展示值 | 约 39.5% 非空 |
| `shares` | 分享、转发或扩散相关展示值 | 约 34.2% 非空 |
| `favorites` | 收藏数或收藏展示值 | 约 34.3% 非空 |
| `views` | 播放、浏览或观看相关展示值 | 约 39.0% 非空 |
| `duration` | 视频时长或播放时长展示文本 | 约 28.0% 非空 |

这些字段当前多为字符串，例如 `1.2万赞`、`67.1亿`、`1250.0万+`。进入统计建模前必须统一转成数值。

### 2.3 采集与任务字段

与采集过程有关的字段包括：

| 字段 | 含义 |
|---|---|
| `created_at` | 本次采集记录生成时间 |
| `task_id` | 采集任务 ID |
| `group_key` | 任务分组键 |
| `device_id` | 采集设备 |
| `client_id` | 采集客户端 |
| `app_name` | 平台名称 |
| `app_package` | 平台包名 |
| `page_type` | 页面类型 |
| `macro_name` | 采集宏任务名称 |

在当前数据中，`created_at` 是最稳定的时间字段。若没有更可靠的发布时间，应把 `created_at` 定义为观测时间，而不是内容发布时间。

### 2.4 匹配和筛选字段

与任务筛选有关的字段包括：

| 字段 | 含义 | 当前情况 |
|---|---|---|
| `active_match_state` | 当前内容匹配状态 | `neutral`、`positive`、`matched` 三类 |
| `active_match_reason` | 自动判断或人工规则给出的匹配原因 | 约 99.5% 非空 |
| `conformity` | 是否符合筛选条件 | 13,705 条为 `True` |
| `sentiment_tags` | 关键词及情绪标签 JSON | 基本全量存在 |

这些字段可以构造事件相关性、正向命中比例和语义热度指标，但不应直接替代事件标签。

## 3. 当前数据能支持的分析单位

PDF 中的目标数据结构是多平台、事件、时间的面板数据。可记平台集合为 $\mathcal{P}$，事件为 $e$，时间窗为 $t$，平台 $p$ 在事件 $e$、时间 $t$ 的第 $k$ 个行为统计量为 $y_{k,p,e,t}$。

当前 CSV 的原始单位不是 $p \times e \times t$ 面板，而是内容级采集记录。因此需要先完成两次转换：

1. 内容记录到事件记录：为每条内容确定所属事件 $e$。
2. 内容记录到时间窗统计量：按平台 $p$、事件 $e$ 和时间窗 $t$ 聚合出多个统计量 $y_{k,p,e,t}$。

完成后，每个平台在一个事件和一个时间窗内应形成一个行为向量：

$$
\mathbf{y}_{p,e,t}
=
(y_{1,p,e,t},\dots,y_{K_p,p,e,t})^\top .
$$

这里 $K_p$ 可以因平台而异。例如，B 站可以使用播放、点赞、评论、收藏、分享等指标；小红书可以使用点赞、收藏、评论、笔记数等指标；抖音和快手可以使用播放、点赞、评论、分享、短视频条数等指标。

## 4. 需要补齐的数据

### 4.1 事件标签

当前数据缺少明确的 `event_id` 或 `event_name`。`task_id` 和 `group_key` 更像采集任务编号，不能直接等同于传播事件。进入 PCA 前至少需要补出以下字段：

| 建议字段 | 含义 |
|---|---|
| `event_id` | 稳定事件 ID |
| `event_name` | 事件名称 |
| `event_type` | 事件类型，如赛事、球星、争议、新闻、直播等 |
| `event_keywords` | 事件关键词集合 |
| `event_start_time` | 事件开始时间或外部触发时间 |

事件标签可以先用关键词规则生成，再抽样人工校验。对世界杯主题数据，可先围绕 `世界杯`、`美加墨世界杯`、`梅西`、`C罗`、`哈兰德`、国家队、比分和比赛名称建立事件词表。

### 4.2 平台原始内容 ID 或 URL

当前 `id` 是采集侧生成 ID，不一定是平台原始内容 ID。若后续需要去重、补爬或追踪同一内容的互动量变化，需要补齐：

| 建议字段 | 含义 |
|---|---|
| `platform_content_id` | 平台原始内容 ID |
| `content_url` | 内容链接 |
| `author_id` | 平台原始作者 ID |

如果无法补齐，应记录去重规则和不可追踪的限制。

### 4.3 外生事件与平台背景变量

PCA 前不一定使用外生变量，但应尽早准备，以免后续动力学模型把外部冲击误认为平台间协同。建议补充：

| 变量类型 | 示例 |
|---|---|
| 赛事节点 | 开球时间、比分、进球、红牌、晋级、爆冷 |
| 新闻节点 | 官宣、争议、突发新闻、采访 |
| 时间周期 | 小时、星期、节假日、工作日 |
| 平台背景 | 平台总采集量、总推荐流量、热榜位置、搜索词 |
| 账号属性 | 作者粉丝数、账号类型、是否官方媒体 |

这些变量在 PCA 前主要用于周期矫正和异常冲击标记。

## 5. PCA 前预处理流程

### 5.1 原始读取与字段保留

读取 CSV 时应使用 UTF-8 BOM 编码。保留三类字段：

1. 标识字段：`id`、`app_name`、`task_id`、`group_key`、`created_at`、`page_type`。
2. 内容字段：`title`、`content`、`media_summary`、`author`、`region`、`publish_time`。
3. 指标字段：`likes`、`comments`、`shares`、`favorites`、`views`、`duration`、`active_match_state`、`conformity`、`sentiment_tags`。

采集侧账号、设备和客户端字段应作为审计信息保留，但不进入注意力指标。对外共享数据时应脱敏 `device_id`、`client_id`、`user_id` 和 `username`。

### 5.2 时间字段处理

主时间轴建议使用 `created_at`，并明确其含义是采集观测时间。处理步骤：

1. 解析为带时区时间戳。
2. 转换到统一时区。
3. 根据研究粒度生成 `time_bin`，优先使用小时粒度。
4. 标记日期、小时、星期和是否周末。

`publish_time` 只作为辅助字段使用。由于其缺失率高且存在异常日期，不应直接作为面板时间轴。

### 5.3 互动指标数值化

将 `likes`、`comments`、`shares`、`favorites`、`views` 统一转换为非负数值：

| 原始形式 | 转换规则 |
|---|---|
| `1.2万`、`1.2万赞` | 乘以 10,000 |
| `67.1亿` | 乘以 100,000,000 |
| `1250.0万+` | 去掉 `+` 后乘以 10,000，并保留截断标记 |
| 空值 | 保留缺失，不直接填 0 |
| 无法解析文本 | 置为缺失并记录解析失败 |

转换后建议生成新字段，例如 `likes_num`、`comments_num`、`shares_num`、`favorites_num`、`views_num`。原始字符串字段保留，便于审计。

### 5.4 内容清洗与去重

内容级数据存在重复采集和相似卡片。推荐按以下层级去重：

1. 若有平台原始内容 ID，则按 `app_name + platform_content_id` 去重。
2. 若无原始 ID，则按 `app_name + author + title + content` 精确去重。
3. 对列表页卡片和详情页同时存在的情况，优先保留详情页，或合并两者指标。
4. 对同一内容在不同时间被重复采集的记录，若要研究互动量变化，应保留时间序列；若只做内容供给统计，应保留首次观测。

去重策略必须和目标指标一致。若指标是某小时内平台上被观察到的内容曝光，重复采集可能代表采集过程而不是用户曝光，不能简单计为多次内容出现。

### 5.5 事件归属

进入面板聚合前，每条内容需要一个或多个事件标签。建议生成：

| 字段 | 说明 |
|---|---|
| `event_id` | 主事件 |
| `event_score` | 内容与事件的相关性分数 |
| `event_rule` | 命中的关键词、模型或人工规则 |
| `event_is_primary` | 是否作为主事件计入 |

事件归属可以分三步：

1. 使用 `title + content + media_summary + sentiment_tags` 做关键词命中。
2. 用 `active_match_state`、`active_match_reason` 和 `conformity` 辅助过滤。
3. 抽样人工校验，修正误命中和无关直播、广告、泛娱乐内容。

对于一条内容命中多个事件的情况，应在聚合前确定是多标签计入、按权重分摊，还是只保留主事件。

### 5.6 聚合为平台-事件-时间面板

清洗后按 `app_name`、`event_id`、`time_bin` 聚合。建议先构造以下指标：

| 指标类别 | 面板统计量 |
|---|---|
| 内容供给 | 内容数、唯一作者数、详情页内容数、短视频流内容数 |
| 基础互动 | 总点赞、总评论、总分享、总收藏、总播放 |
| 稳健互动 | 中位点赞、P90 点赞、非零互动内容比例 |
| 相关性 | 符合筛选内容数、`conformity=True` 比例、`matched/positive` 内容数 |
| 语义热度 | 事件关键词出现次数、核心球星或球队关键词频次 |
| 情绪结构 | 正向、中性、负向关键词计数或比例 |

聚合后的目标表应至少包含：

| 字段 | 含义 |
|---|---|
| `platform` | 平台 |
| `event_id` | 事件 |
| `time_bin` | 时间窗 |
| `n_content` | 内容数 |
| `n_author` | 作者数 |
| `sum_likes` | 总点赞 |
| `sum_comments` | 总评论 |
| `sum_shares` | 总分享 |
| `sum_favorites` | 总收藏 |
| `sum_views` | 总播放或浏览 |
| `match_rate` | 筛选命中比例 |
| `keyword_count_*` | 关键词计数 |
| `sentiment_count_*` | 情绪计数 |

如果某平台不存在某项指标，不应强制填 0。应保留平台可用指标集合 $K_p$，后续每个平台分别标准化和降维。

### 5.7 缺失值处理

缺失值需要区分三类：

| 缺失类型 | 处理方式 |
|---|---|
| 平台不提供该指标 | 记为结构性缺失，不参与该平台 PCA |
| 内容没有展示该指标 | 保留缺失，聚合时按可观测值统计，并记录覆盖率 |
| 时间窗没有相关内容 | 面板中补齐该时间窗，计数类指标置 0，比例类指标置缺失或 0，并明确规则 |

建议为每个聚合指标同时记录覆盖率，例如 `likes_coverage`、`views_coverage`。覆盖率太低的指标不应进入 PCA。

### 5.8 异常值处理

当前互动指标存在极端值，可能来自账号总量、直播间指标、平台聚合数或解析误差。进入对数变换前需要处理异常：

1. 对每个平台、每个指标分别检查分布。
2. 标记超过平台内 P99 或 P99.5 的记录。
3. 人工抽查最大值，判断是否为单条内容指标。
4. 对确认保留的重尾值使用截尾，而不是删除。
5. 对明显不是单条内容的值置为缺失或单独标记。

建议在内容级和面板级都保留异常标记，避免极少数头部内容支配第一主成分。

### 5.9 对数变换

对非负计数型面板指标使用：

$$
\tilde{y}_{k,p,e,t}
=
\log(1+y_{k,p,e,t}) .
$$

对比例型指标，如 `match_rate` 或情绪比例，不做 `log(1+y)`，而是根据分布选择原值、logit 变换或 arcsine-square-root 变换。若比例存在大量 0 或 1，需要加小常数并记录处理规则。

### 5.10 周期项与平台背景矫正

社媒数据有明显小时周期和日期周期。若不矫正，PCA 的第一主成分可能主要反映平台自然活跃度，而不是事件相关注意力。建议对每个平台和每个指标分别拟合基线模型：

$$
\tilde{y}_{k,p,e,t}
=
s_{k,p}(\mathrm{hour}_t,\mathrm{weekday}_t)
+
b_{k,p,t}
+
r_{k,p,e,t}.
$$

其中 $s_{k,p}$ 表示小时和星期周期，$b_{k,p,t}$ 表示平台背景趋势，$r_{k,p,e,t}$ 是去除周期后的残差。若缺少平台大盘流量，可以先用全事件总量或全任务总采集量近似背景项。

进入 PCA 的候选值应优先使用残差或经周期矫正后的值，而不是原始计数。

### 5.11 平台内标准化

在完成异常处理、对数变换和周期矫正后，对每个平台和每个指标做标准化：

$$
z_{k,p,e,t}
=
\frac{r_{k,p,e,t}-\mu_{k,p}}{\sigma_{k,p}} .
$$

这里 $\mu_{k,p}$ 和 $\sigma_{k,p}$ 应只在训练期估计，并固定用于验证期和测试期。若当前阶段只是探索性分析，也应记录估计样本范围，避免后续复现实验时发生时间泄漏。

标准化后，每个平台形成 PCA 输入向量：

$$
\mathbf{z}_{p,e,t}
=
(z_{1,p,e,t},\dots,z_{K_p,p,e,t})^\top .
$$

该向量就是 PCA 前的最终数据形态。

## 6. PCA 前质量检查

在进入 PCA 之前，应完成以下检查：

1. 每个平台、每个事件、每个时间窗是否形成完整面板。
2. 每个指标的缺失率、零值率和覆盖率是否可接受。
3. 数值化后的互动指标是否仍有明显解析错误。
4. 截尾前后分布是否合理。
5. 事件标签抽样准确率是否足够。
6. 周期矫正后是否仍保留事件峰值。
7. 标准化后每个平台内各指标均值是否接近 0、标准差是否接近 1。
8. 不同平台的指标集合是否被分别处理，而不是强行合并到同一列空间。

只有这些检查通过后，才适合对每个平台的 $\mathbf{z}_{p,e,t}$ 分别执行 PCA。

## 7. 最小可执行版本

如果先做一个可运行的探索版，建议采用以下最小流程：

1. 使用 `created_at` 生成小时级 `time_bin`。
2. 用关键词规则生成 `event_id`，先聚焦世界杯、梅西、C罗、哈兰德、美加墨世界杯等高频事件。
3. 将 `likes`、`comments`、`shares`、`favorites`、`views` 数值化。
4. 按 `app_name + author + title + content` 做保守去重。
5. 聚合出 `n_content`、`n_author`、`sum_likes`、`sum_comments`、`sum_shares`、`sum_favorites`、`sum_views`、`match_rate`。
6. 对平台内每个指标做 P99 截尾和 `log(1+y)`。
7. 加入小时和星期周期矫正。
8. 按平台和指标标准化，得到 $\mathbf{z}_{p,e,t}$。

这个版本已经可以作为 PCA 的输入，但仍需在报告中明确两点限制：时间轴是采集观测时间，不是内容发布时间；事件标签来自规则或弱监督，不是完全人工标注。
